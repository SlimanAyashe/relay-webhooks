# Failure modes

The running "if it dies/misbehaves here, then what — and which test proves it" reference,
kept as one row per phase per the project plan's comprehension-forcing function. This is meant
to be readable standalone: pick a row, and the test it names can be run directly to watch the
claimed behavior happen.

| Failure point | Expected behavior | Proof |
| --- | --- | --- |
| Duplicate `POST /v1/events` with the same `Idempotency-Key` and an identical body | The original event is returned unchanged (same id, same `202`); no second row is inserted | `tests/integration/test_event_ingest_service.py::test_duplicate_key_identical_body_returns_original_no_new_row` (asserts a raw `COUNT(*)` of 1), `tests/integration/test_events_router.py::test_ingest_duplicate_key_identical_body_returns_same_event` |
| Duplicate `POST /v1/events` with the same `Idempotency-Key` but a differing body | `409 Conflict`, via the shared `application/problem+json` envelope | `tests/integration/test_event_ingest_service.py::test_duplicate_key_differing_body_raises_conflict_no_new_row`, `tests/integration/test_error_handling.py::test_409_conflict_response_matches_rfc9457_shape` |
| Two requests race to insert the same `(tenant_id, Idempotency-Key)` at the same instant | The DB's `UNIQUE` constraint lets exactly one `INSERT` win; the loser's repository call raises `IdempotencyKeyConflict`, caught inside a `SAVEPOINT` so the surrounding transaction stays usable, and resolved the same identical-body-vs-differing-body way as an ordinary duplicate | `tests/integration/test_event_repository.py::test_duplicate_idempotency_key_raises_typed_conflict` (also proves the session survives the conflict) |
| Revoked API key presented on any `/v1/*` request | `401`, before any route handler code runs | `tests/integration/test_auth.py::test_authenticate_rejects_revoked_key`, `tests/integration/test_tenant_isolation.py::test_revoked_api_key_returns_401` |
| Malformed, unknown-prefix, or missing API key presented | `401` — the same generic detail as a revoked key, so a response can't be used to distinguish "doesn't exist" from "exists but revoked" | `tests/integration/test_auth.py::test_authenticate_rejects_malformed_key`/`test_authenticate_rejects_unknown_prefix`, `tests/integration/test_tenant_isolation.py::test_malformed_api_key_returns_401`/`test_unknown_api_key_returns_401`/`test_missing_api_key_returns_401` |
| Valid API key from tenant A used against tenant B's endpoint (`GET`/`PATCH`/`DELETE`) | `404`, not `403` — tenant A's key can't distinguish "doesn't exist" from "belongs to someone else," so existence is never leaked across tenants | `tests/integration/test_tenant_isolation.py::test_tenant_a_key_cannot_read_or_modify_tenant_b_endpoint` |
| Valid API key lacking the scope a request needs | `403 Forbidden` | `tests/integration/test_auth.py::test_require_scope_rejects_key_without_scope`, `tests/integration/test_endpoints_router.py::test_wrong_scope_returns_403` |
| Client-supplied cursor on `GET /v1/endpoints` is malformed or forged | `422`, not a 500 or a silently-wrong page | `tests/unit/test_pagination.py::test_decode_cursor_rejects_garbage_input`, `tests/integration/test_endpoints_router.py::test_list_endpoints_rejects_invalid_cursor` |
| An unexpected/unhandled exception occurs anywhere in a request | `500` with a bare, generic problem+json body and a `trace_id` a caller can quote back — never a stack trace or exception message on the wire; full context is logged server-side instead | `tests/unit/test_errors.py::test_domain_error_handler_maps_unmapped_subclass_to_500` |
| The event-ingest transaction commits (event + outbox row), but the relay hasn't published it yet — standing in for a relay process that died or hadn't started | The outbox row is simply still `pending` in Postgres; the next relay run (a restart, or the same process's next tick) finds and fans it out. There is no special recovery path because there was nothing to recover, only to notice | `tests/integration/test_relay_worker.py::test_outbox_row_committed_before_a_relay_run_is_recovered_on_the_next_run` |
| Two relay instances race to claim the same due outbox row | `SELECT ... FOR UPDATE SKIP LOCKED` gives the row to exactly one of them; the other sees nothing rather than blocking or double-claiming | `tests/integration/test_outbox_repository.py::test_skip_locked_gives_a_claimed_row_to_exactly_one_concurrent_claimer` |
| A dispatcher reads a delivery message (`XREADGROUP`) and dies before acking it | The message stays in the consumer group's pending-entries list; the reaper's `XAUTOCLAIM` sweep reclaims it once it's idle past the configured threshold, reprocesses it through the same delivery logic, and acks the original message ID | `tests/integration/test_reaper_worker.py::test_run_once_reclaims_and_processes_a_message_a_dead_consumer_never_acked` |
| A worker successfully sends the HTTP request but dies before acking the stream message | The message is redelivered (via reclaim) and attempted again, so the receiver observes a genuine duplicate — this is the concrete case that proves exactly-once external side effects are impossible by design, and why receivers must be idempotent | `tests/integration/test_dispatcher_worker.py::test_redelivery_after_a_post_send_pre_ack_crash_produces_an_observable_duplicate` |
| Destination returns a non-2xx response (e.g. 500) | The attempt is recorded with `error_class=http_error`; the delivery moves to `retrying` with `next_retry_at` set within the full-jitter backoff bound for that attempt number | `tests/integration/test_dispatcher_worker.py::test_process_delivery_message_on_500_schedules_jittered_backoff` |
| Destination connection times out mid-response | The attempt is recorded with `error_class=timeout` and no response status; the delivery moves to `retrying`, never `delivered` | `tests/integration/test_dispatcher_worker.py::test_process_delivery_message_records_timeout_not_success` |
| A scheduled retry's `next_retry_at` becomes due | The scheduler's tick pops it from the Redis ZSET (atomically, via a Lua script) and re-`XADD`s it onto the delivery stream exactly once; entries not yet due are left untouched | `tests/integration/test_scheduler_worker.py::test_run_once_fires_only_due_retries` |
| An endpoint's consecutive delivery-attempt failures reach the breaker threshold | Breaker flips `closed -> open` (`opened_at` recorded); further attempts are deferred without an HTTP call being made until the cooldown elapses, then exactly one probe is allowed (`open -> half_open`); the probe succeeding closes it (`half_open -> closed`) | `tests/unit/test_breaker.py` (pure state-transition table, including the full cycle), `tests/integration/test_circuit_breaker.py::test_full_breaker_cycle_closed_open_half_open_closed` (testing scenario #10, against a real Postgres-backed endpoint row, driven through `process_delivery_message` with `freezegun` fast-forwarding past the cooldown) |
| A destination redirects to a forbidden address (loopback/RFC1918/link-local/CGNAT/IPv6 ULA/`169.254.169.254`) | The redirect hop's `Location` is re-validated by the SSRF guard before any connection to it is attempted; the attempt is recorded with `error_class=ssrf_blocked`, not a generic connection failure, and no socket ever reaches the forbidden address | `tests/integration/test_http_sender_ssrf.py::test_redirect_to_forbidden_ip_is_blocked_with_no_connection_made` (testing scenario #11 -- redirect-to-metadata case), `tests/integration/test_dispatcher_worker.py::test_ssrf_blocked_result_is_recorded_and_retried_not_dropped` |
| A destination's DNS record rebinds between the SSRF guard's resolution and the HTTP client connecting (the TOCTOU window a naive guard leaves open) | The IP-pinned transport connects to the address the guard actually validated, never re-resolving mid-request, so a rebind after validation has no effect on that attempt | `tests/integration/test_http_sender_ssrf.py::test_dns_rebinding_connects_to_the_originally_validated_ip_not_a_fresh_lookup` |
| A tenant exceeds its configured per-second event-ingest rate | `429` with a `Retry-After` header computed from the token bucket's own refill math, via the shared `application/problem+json` envelope; other tenants' budgets are unaffected | `tests/integration/test_events_router.py::test_exceeding_the_rate_limit_returns_429_with_retry_after`, `tests/integration/test_events_router.py::test_rate_limit_is_isolated_per_tenant`, `tests/integration/test_rate_limit.py` (token-bucket math in isolation) |
| A delivery's attempt count reaches the configured retry budget without succeeding | The delivery moves to `DeliveryState.DEAD` (`deliveries WHERE state='dead'` is the DLQ, no separate table) instead of scheduling another retry | `tests/integration/test_dispatcher_worker.py::test_retry_budget_exhaustion_moves_delivery_to_dead`, `tests/integration/test_delivery_repository.py::test_mark_dead_sets_terminal_state_and_increments_attempts` |
| A dead delivery is replayed via `POST /v1/deliveries/{id}/replay` | It resets to `pending` with a fresh retry budget and is re-enqueued to the delivery stream; the original (exhausted) `delivery_attempts` rows are never modified and stay queryable, and new attempts after replay are appended, not merged into the old chain | `tests/integration/test_replay_service.py::test_replay_preserves_original_attempt_history_while_new_attempts_go_forward`, `tests/integration/test_deliveries_router.py::test_replay_dead_delivery_resets_state_and_returns_202` |
| One endpoint is slow (not failing -- the breaker doesn't trip) but has many deliveries in flight at once | A per-endpoint semaphore caps its concurrent in-flight attempts regardless of overall dispatcher concurrency headroom, so it can't consume the whole worker pool's capacity | `tests/integration/test_dispatcher_per_endpoint_concurrency.py::test_per_endpoint_semaphore_caps_concurrent_attempts_against_one_endpoint` |
| A payload is tampered with in transit, or an outbound request is replayed outside the tolerance window | `verify()` (constant-time via `hmac.compare_digest`) rejects a tampered payload's signature and rejects a correctly-signed request whose timestamp is outside `signature_tolerance_seconds` of "now" in either direction | `tests/unit/test_signing.py` (hypothesis-generated payloads/timestamps) |
| A sandbox key is presented after its 60-minute TTL elapses | `401` — the same generic detail as a revoked or malformed key, via `ApiKey.is_expired()` checked alongside `is_revoked()` in `_authenticate` | `tests/integration/test_auth.py::test_authenticate_rejects_expired_sandbox_key` (freezegun, no real wait) |
| A sandbox tenant registers past its fixed endpoint count | `403`, via `SandboxQuotaExceeded` — independent of, and far tighter than, the per-tenant rate limiter every tenant is subject to; a no-op for a normal (non-sandbox) tenant | `tests/integration/test_sandbox_service.py::test_endpoint_quota_rejects_the_endpoint_at_the_cap`, `tests/integration/test_sandbox_router.py::test_sandbox_endpoint_quota_rejects_the_endpoint_at_the_cap` |
| A sandbox tenant ingests past its fixed event count | `403`, same mechanism as the endpoint cap, checked independently of the sandbox's own tighter rate limit | `tests/integration/test_sandbox_service.py::test_event_quota_rejects_the_event_at_the_cap`, `tests/integration/test_sandbox_router.py::test_sandbox_event_quota_rejects_the_event_at_the_cap` |
| Two sandboxes have live SSE connections open at once | Each subscriber's `GET /v1/sandbox/stream` connection is scoped to its own tenant's Redis Pub/Sub channel by construction (one channel per tenant id); another tenant's attempt events are never received, not filtered out after the fact | `tests/integration/test_attempt_events.py::test_subscriber_receives_only_events_published_for_its_own_tenant` |
| The console's `redirect-to-metadata` mock receiver is registered as a destination and triggered | Same as any other redirect to a forbidden address (row above): the attempt is recorded with `error_class=ssrf_blocked`, no connection to `169.254.169.254` is ever made | `tests/unit/test_mock_router.py::test_redirect_to_metadata_returns_a_redirect_to_the_metadata_ip` (the route's own response shape), `tests/integration/test_mock_redirect_to_metadata_ssrf.py::test_redirect_to_metadata_mock_is_blocked_end_to_end_with_no_connection_made` (driven through the real delivery pipeline) |
| A client IP repeatedly calls `POST /v1/sandbox` | `429` with `Retry-After`, via the same Redis-backed token bucket the per-tenant limiter uses, keyed on the client IP instead of a tenant id | `tests/integration/test_sandbox_router.py::test_sandbox_creation_is_rate_limited_per_ip` |
| An event ingest body exceeds the configured max payload size | `413`, either at the ASGI layer (declared `Content-Length` over the limit, rejected before the body is read) or, if `Content-Length` under-reports the truth, re-checked once the body is actually in hand | `tests/unit/test_max_body_size_middleware.py`, `tests/integration/test_events_router.py::test_oversized_payload_returns_413` |
